# Правила для ИИ агента при работе с проектом Bismarck Game

## Общие принципы

При выполнении любых задач (проектирование решений, анализ кода, внесение изменений) ИИ агент **ОБЯЗАН** проверять соответствие решения правилам игры и архитектуре проекта.

## Обязательные проверки

### 1. Проверка соответствия правилам игры

**Источник:** `docs/Правила.md`

**Когда проверять:**
- При проектировании новой функциональности
- При анализе существующего кода
- При внесении изменений в игровую логику
- При реализации фаз игры
- При работе с юнитами, движением, поиском, боем

**Что проверять:**
- Соответствие игровых механик правилам из `docs/Правила.md`
- Корректность реализации фаз игры (Visibility, Shadow, Movement, Search, Air Attack, Naval Combat, Chance, Admin)
- Правильность расчета факторов поиска
- Соответствие правилам движения и расхода топлива
- Корректность обработки видимости и обнаружения
- Правильность расчета боевых действий

**Действия:**
- Если обнаружено несоответствие правилам → **НЕМЕДЛЕННО** сообщить пользователю
- Предложить исправление с указанием конкретного правила из `docs/Правила.md`
- **ЗАПРЕЩЕНО** вносить изменения в `docs/Правила.md` (это источник истины)

### 2. Проверка соответствия архитектуре

**Источник:** `docs/ARCHITECTURE.md`

**Когда проверять:**
- При проектировании новой функциональности
- При анализе существующего кода
- При внесении изменений в структуру проекта
- При создании новых сервисов или компонентов
- При изменении структуры данных

**Что проверять:**
- Соответствие структуре проекта (backend/frontend разделение)
- Использование GameModel как единого источника истины
- Правильность использования GameStateService для работы с состоянием
- Корректность фильтрации данных через ViewModelService
- Соответствие паттернам и принципам архитектуры
- Правильность использования трехуровневого кэширования
- Соответствие фазам игры через PhaseManager

**Действия:**
- Если обнаружено несоответствие архитектуре → **НЕМЕДЛЕННО** сообщить пользователю
- Предложить исправление с указанием конкретного раздела из `docs/ARCHITECTURE.md`

## Процедура внесения изменений в архитектуру

### Шаг 1: Обнаружение необходимости изменений

Если при работе с кодом обнаружена необходимость изменения архитектуры:

1. **Остановиться** и не вносить изменения автоматически
2. **Проанализировать** текущую архитектуру в `docs/ARCHITECTURE.md`
3. **Определить** конкретные изменения, которые необходимы
4. **Обосновать** необходимость изменений

### Шаг 2: Предложение изменений

**Обязательно предоставить:**

1. **Описание проблемы:**
   - Что не соответствует текущей архитектуре
   - Почему текущая архитектура не подходит
   - Какие проблемы это создает

2. **Предлагаемые изменения:**
   - Конкретные изменения в `docs/ARCHITECTURE.md`
   - Обоснование каждого изменения
   - Влияние на существующий код

3. **План реализации:**
   - Какие файлы нужно изменить
   - Какие компоненты затронуты
   - Оценка сложности изменений

**Формат предложения:**

```
## Предложение изменения архитектуры

### Проблема
[Описание проблемы]

### Текущее состояние (из ARCHITECTURE.md)
[Цитата из ARCHITECTURE.md]

### Предлагаемое изменение
[Описание изменения]

### Обоснование
[Почему это изменение необходимо]

### Влияние на код
[Какие файлы/компоненты затронуты]

### План реализации
[Шаги реализации]
```

### Шаг 3: Ожидание согласования

**ЗАПРЕЩЕНО:**
- Вносить изменения в `docs/ARCHITECTURE.md` без явного согласия пользователя
- Продолжать работу, игнорируя несоответствие архитектуре
- Вносить изменения "на будущее" без согласования

**ОБЯЗАТЕЛЬНО:**
- Дождаться явного согласия пользователя
- Уточнить детали, если предложение неясно
- Предложить альтернативные решения, если возможно

### Шаг 4: Внесение изменений

После получения согласия:

1. **Обновить** `docs/ARCHITECTURE.md` с предложенными изменениями
2. **Обновить** код в соответствии с новой архитектурой
3. **Проверить** соответствие всех изменений обновленной архитектуре
4. **Убедиться**, что изменения не нарушают существующую функциональность

## Запрещенные действия

### ❌ ЗАПРЕЩЕНО изменять `docs/Правила.md`

**Причина:** Это источник истины для правил игры. Изменения могут нарушить соответствие реализации правилам.

**Что делать вместо этого:**
- Если обнаружена ошибка в правилах → сообщить пользователю
- Если правила неясны → запросить уточнение у пользователя
- Если нужно дополнить правила → предложить создание отдельного документа

### ❌ ЗАПРЕЩЕНО игнорировать проверки

**Причина:** Нарушение правил или архитектуры может привести к серьезным проблемам в проекте.

**Что делать:**
- Всегда проверять соответствие перед внесением изменений
- Если проверка сложная → разбить на этапы
- Если не уверен → спросить у пользователя

### ❌ ЗАПРЕЩЕНО вносить изменения в архитектуру без согласования

**Причина:** Архитектура - это фундамент проекта. Изменения должны быть обдуманными и согласованными.

**Что делать:**
- Всегда предлагать изменения явно
- Ждать согласия перед внесением
- Документировать все изменения в `docs/ARCHITECTURE.md`

## Примеры использования

### Пример 1: Реализация новой фазы игры

**Проверки:**
1. ✅ Соответствие правилам фазы из `docs/Правила.md`
2. ✅ Использование PhaseManager из архитектуры
3. ✅ Интеграция с GameModel
4. ✅ Обновление GameStateService при изменении состояния

**Действия:**
- Проверить правила фазы в `docs/Правила.md`
- Убедиться, что используется PhaseManager
- Проверить, что изменения сохраняются в GameModel
- Убедиться, что используется GameStateService.UpdateGameModel()

### Пример 2: Добавление нового сервиса

**Проверки:**
1. ✅ Соответствие структуре проекта из `docs/ARCHITECTURE.md`
2. ✅ Правильная инициализация в Server
3. ✅ Dependency Injection через конструкторы
4. ✅ Интеграция с GameStateService, если нужно обновлять GameModel

**Действия:**
- Если сервис должен обновлять GameModel → использовать GameStateService
- Если сервис должен фильтровать данные → использовать ViewModelService
- Если сервис должен работать с фазами → интегрировать с PhaseManager
- Если структура проекта не подходит → **предложить изменение архитектуры**

### Пример 3: Изменение структуры данных

**Проверки:**
1. ✅ Соответствие GameModel из `docs/ARCHITECTURE.md`
2. ✅ Не нарушает ли существующий код
3. ✅ Правильно ли обновляется версия GameModel

**Действия:**
- Если изменение затрагивает GameModel → **предложить изменение архитектуры**
- Убедиться, что версионирование работает корректно
- Проверить, что ViewModelService правильно обрабатывает новые данные

## Чек-лист перед внесением изменений

Перед внесением любых изменений в код:

- [ ] Проверено соответствие правилам из `docs/Правила.md`
- [ ] Проверено соответствие архитектуре из `docs/ARCHITECTURE.md`
- [ ] Если нужно изменить архитектуру → предложение подготовлено и отправлено пользователю
- [ ] Получено согласие на изменения архитектуры (если применимо)
- [ ] Изменения в `docs/ARCHITECTURE.md` внесены (если согласованы)
- [ ] Код соответствует обновленной архитектуре
- [ ] Не внесены изменения в `docs/Правила.md`

## Приоритеты

1. **Высший приоритет:** Соответствие `docs/Правила.md` (источник истины для правил игры)
2. **Высокий приоритет:** Соответствие `docs/ARCHITECTURE.md` (фундамент проекта)
3. **Средний приоритет:** Оптимизация и улучшения (только если не нарушают правила и архитектуру)
4. **Низкий приоритет:** Косметические изменения

## Важные напоминания

- **`docs/Правила.md`** - это источник истины для правил игры. Изменения **ЗАПРЕЩЕНЫ**.
- **`docs/ARCHITECTURE.md`** - это описание архитектуры проекта. Изменения требуют **согласования**.
- Всегда проверяйте соответствие перед внесением изменений.
- При сомнениях - спрашивайте у пользователя.
- Лучше предложить изменение и подождать согласия, чем внести неправильное изменение.
