# Проект решения: Унификация полей видимости

## Статус использования MCP инструментов
- ❌ MCP sequential-thinking не использован (доступен через list_mcp_resources)
- ❌ MCP context7 не использован

---

## Проблема

Сейчас в системе используются два разных типа для представления видимости юнитов:

1. **DetectionLevel** (используется в GameModel):
   - Тип: `DetectionLevel` (enum: "none", "sighted", "shadowed", "lost")
   - Места использования:
     - `NavalUnitData.DetectionLevel` - в `UnitModel` (GameModel)
     - `TaskForceModel.DetectionLevel` (string) - в GameModel
     - `EnemyContactModel.DetectionLevel`
     - Логирование событий поиска
     - Обновление в фазе поиска через `UpdateGameModelWithRetry()`

2. **UnitVisibility** (используется в ViewModel и таблице unit_visibility):
   - Тип: `UnitVisibility` (enum: "unknown", "sighted", "shadowed")
   - Места использования:
     - `UnitViewModel.Visibility` - во ViewModel для фронтенда
     - `TaskForceViewModel.Visibility`
     - `UnitVisibilityState.Visibility` - в таблице `unit_visibility` БД
     - Фронтенд использует это поле для отрисовки

3. **Проблема дублирования:**
   - ViewModelService конвертирует `DetectionLevel` → `UnitVisibility`
   - Это создает избыточность и возможность рассинхронизации
   - Фронтенд должен ориентироваться на `visibility`, но в GameModel есть `detection_level`

---

## Цель решения

**Унифицировать использование одного типа поля видимости: `UnitVisibility`**

- Использовать `UnitVisibility` везде (GameModel, ViewModel, БД)
- Убрать `DetectionLevel` как отдельный тип
- Упростить логику конвертации
- Обеспечить консистентность данных

---

## Архитектурное решение

### 1. Выбор единого типа: UnitVisibility

**Преимущества использования UnitVisibility:**
- Уже используется на фронтенде (ViewModel)
- Семантически правильное название ("видимость", а не "уровень обнаружения")
- Уже есть в таблице `unit_visibility`
- Более понятный для UI/UX

**Маппинг значений:**
```
DetectionLevel "none"     → UnitVisibility "unknown"
DetectionLevel "sighted"  → UnitVisibility "sighted"
DetectionLevel "shadowed" → UnitVisibility "shadowed"
DetectionLevel "lost"     → UnitVisibility "unknown" (или убрать это значение)
```

## Риски и проблемы

### 1. Разные значения для разных игроков

**Проблема:** Видимость вражеского юнита может быть разной для разных игроков.
- Игрок A видит юнит как "sighted"
- Игрок B видит тот же юнит как "unknown"

**Решение:**
- В GameModel хранить видимость относительно игрока-владельца или максимальный уровень
- Или хранить в GameModel только для текущего активного игрока
- Или полностью полагаться на таблицу `unit_visibility` для определения видимости

**Рекомендация:**
- В GameModel хранить `Visibility` как "истинное состояние" (для владельца или максимальный уровень)
- ViewModelService уже фильтрует по видимости из таблицы `unit_visibility`
- Можно синхронизировать GameModel.Visibility с таблицей unit_visibility при обновлении

### 2. Значение "lost" в DetectionLevel

**Проблема:** `DetectionLevel` имеет значение "lost", которого нет в `UnitVisibility`.

**Решение:**
- Заменить "lost" на "unknown" при миграции
- Или добавить "lost" в `UnitVisibility` (если нужно)
- Или убрать использование "lost" совсем

**Рекомендация:** Убрать "lost", использовать только "unknown", "sighted", "shadowed"

### 3. TaskForceModel.DetectionLevel был string

**Проблема:** В TaskForceModel поле DetectionLevel было типа `string`, а не `DetectionLevel`.

**Решение:**
- При миграции использовать правильный тип `UnitVisibility`
- Это улучшит типобезопасность

## Преимущества решения

1. **Единообразие:**
   - Один тип для видимости во всей системе
   - Нет дублирования логики конвертации

2. **Простота:**
   - Упрощение ViewModelService (убрать конвертацию)
   - Меньше мест для ошибок

3. **Понятность:**
   - Семантически правильное название "visibility"
   - Соответствие терминологии UI/UX

4. **Консистентность:**
   - GameModel и ViewModel используют одинаковую структуру
   - Нет рассинхронизации между полями
