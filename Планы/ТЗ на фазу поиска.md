### Техническое задание: реализация фазы поиска (`search_phase`) с требованиями к тестам

#### 1. Общая логика
- Фаза запускается автоматически после движения. Игроки ничего не объявляют вручную — сервер сам проводит поиск.
- Порядок обработки фиксированный: сначала союзники ищут немецкие юниты, затем немцы ищут союзных.
- Для каждой стороны выполняется полный проход по гексам карты; результаты синхронизируются с `VisibilityService` / фронтом.

#### 2. Предварительные проверки
- `visibility_level >= 10`: фазу завершаем сразу; поиск/преследование/бой запрещены, все маркеры `SIGHTED/SHADOWED` должны быть сняты на этапе видимости.
- `is_fog = true`: поиск разрешён, но каждый гекс проверяем через `MapStructureService.IsFogHex`; туманные гексы пропускаем.

#### 3. Расчёт факторов поиска
- Используем `SearchService.CalculateSearchFactors(gameID, hexID, playerSide)`. На вход подаём текущую сторону (`"allied"` или `"german"`).
- Метод возвращает суммарные факторы только ищущей стороны, учитывая:
  - +1 за каж­дый корабль вне ТФ, который допущен к поиску;
  - +1 за каждую ТФ ищущего игрока в гексе;
  - +3 за морской патруль (одиночные корабли и ТФ);
  - +2 за маркеры воздушного поиска (`flight_path_search`);
  - подготовку к учёту «собственных» фактор­ов (поле `search_factors` в `naval_units` и аналог для ТФ — подключить, когда данные появятся).
- Исключения (зарезервировать логику в `canUnitContributeSearchFactors`):
  - корабль выполнял попытку преследования в текущем ходу;
  - корабль заправляется (в порту или море);
  - корабль проводит ремонт в море.
  Сейчас метод возвращает `true`, но содержит `TODO`; после появления данных по этим состояниям нужно будет активировать фильтры.

#### 4. Обработка гекса
Для каждого гекса, где факторы ищущей стороны `>= visibility_level`:
1. Собираем вражеские юниты и ТФ (идентификаторы, классы, участие в ТФ).
2. Определяем наличие маркеров:
   - если есть `flight_path_search` → помечаем найденные объекты как преследуемые (`SetUnitShadowed`, аналоги для ТФ);
   - иначе → помечаем как обнаруженные (`SetUnitSighted`).
3. Обрабатываем особый случай «следов»: если является результатом прохода через гекс, фиксируем текущее местоположение и количество кораблей без постановки маркеров.
4. Отдельно рассматриваем гексы, где присутствуют и одиночные корабли, и ТФ — маркеры выставляем на всё, что обнаружено.

#### 5. Завершение фазы
- После обхода удаляем все маркеры `flight_path_search` у обеих сторон.
- Синхронизируем состояние `unit_visibility` и API (фронт видит актуальные `SIGHTED/SHADOWED`).

#### 6. Требования к тестированию
- **Позитивные сценарии**: союзники обнаруживают немецкий юнит/ТФ; немцы — союзный.
- **Видимость X**: проверка, что фаза сразу завершается и никаких маркеров не ставится.
- **Туман**: гекс с туманом пропускается, соседний — обрабатывается.
- **Маркеры**: наличие/отсутствие `flight_path_search` приводит к разным статусам (`shadowed` vs `sighted`).
- **Смешанные случаи**: в гексе и одиночные корабли, и ТФ; в гексе никого нет, но зафиксирован «след».
- **Заглушки** (`TODO` в `canUnitContributeSearchFactors`): добавить юнит-тесты, подтверждающие, что при текущем состоянии метод возвращает `true`, и оставить пометки на будущее (тесты должны фиксировать ожидаемое поведение, чтобы после добавления логики их можно расширить).  
- В покрытие включить проверку удаления маркеров `flight_path_search` после завершения.

#### 7. Прочее
- Логировать ключевые шаги (гекс, факторы, найденные юниты, выбранный статус).
- Код должен быть устойчив к отсутствию маркеров/юнитов (никаких паник — просто продолжаем цикл).
- Структура должна оставаться расширяемой: по мере добавления статусов преследования/ремонта/заправки они просто подключаются к `canUnitContributeSearchFactors` и базовым проверкам.
